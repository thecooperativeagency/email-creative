Who should own the task?

Use Ada when the job needs judgment, triage, or coordination. Use Luc when the job is clearly operational or technical. Use both only when you mean it.

Start with Ada

Priorities, decision prep, triage, client reply drafts, “what should happen next?”, mixed business/technical situations, or anything messy.

Start with Luc

Repo checks, page edits, debugging, system inspection, implementation, environment issues, or “go do the thing and report back.”

Use both on purpose

Say it explicitly: “Ada coordinate this, Luc do the technical check.” Don’t send the same request to both agents independently and hope it sorts itself out.

The default prompt format

If you use this shape, things stay clean almost automatically.

Best all-purpose format
One owner. One task. One definition of done.
[Ada or Luc]: [task]. Context: [1–2 lines that matter]. Done looks like: [what you want back]. Constraints: [if any].
  • Add “investigate only” when you want diagnosis without changes.
  • Add “fix it” when action is allowed.
  • Add “draft only” when you want prep but no send.
  • Add “send it” only when you really mean external delivery is approved.
  • Add “if blocked, ask once” when you want less back-and-forth.

Good asks vs messy asks

Most chaos starts with vague wording. Tighten the ask and the agents stay sharp.

Good

Specific owner, clear outcome, clear permission level.

Ada: summarize today’s priorities and tell me what needs my decision. Luc: update the SEO page in the repo and send me the preview link. Ada: draft a reply to this client and flag anything risky. Draft only. Luc: check what’s broken vs working in the app. Investigate only.

Messy

Vague asks make ownership fuzzy and invite loops.

Handle this. Look into it. Clean this up. Can y’all both check this? Ok.

The one-owner rule

Pick one owner per task. That alone will prevent most cross-talk.

Do this

“Ada: own this. Use Luc if needed.”

Or this

“Luc: check this directly and report back.”

Not this

Sending the same task to both agents separately and waiting for overlap, drift, or duplicate work.

  • If you switch topics, start a fresh message.
  • If you’re replying to a prior task, reply to that message directly.
  • Don’t assume both agents saw the same context unless you routed it that way.
  • Don’t assume a vague “ok” means the task is now being tracked forever.

Simple workflow that works

This is the easiest way to keep Telegram productive without babysitting it.

1. Pick the owner

Start with Ada for messy coordination. Start with Luc for execution.

2. State the ask

Use the owner/task/context/done/constraints format.

3. Set permission

Say whether it’s investigate only, draft only, fix it, or send it.

4. Expect one of three returns

Result, blocker, or next recommendation. That’s the clean loop.

Three patterns worth memorizing

If you remember nothing else, remember these.

Pattern A — coordination first

“Ada: here’s the issue. Triage it, use Luc if needed, and come back with the answer.”

Pattern B — direct execution

“Luc: check this app/repo/system and tell me what’s broken, what’s working, and your first fix.”

Pattern C — draft then act

“Ada: draft the response. Luc: only step in if there’s a technical change needed.”

Pattern D — parallel on purpose

“Ada summarize; Luc investigate root cause.” Two roles, same problem, no ambiguity.

Useful phrases that save time

These tiny switches make the request much clearer.

Permission / scope

Investigate only. Fix it if it’s safe. Draft, don’t send. Send after review. Don’t message anyone externally. Use AgentOps for the handoff.

Output style

Give me the short version. Give me options with a recommendation. Tell me what needs my decision. If blocked, ask once. Tell me the first fix you’d make.
